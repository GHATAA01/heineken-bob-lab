2 Challenge the Delta Strategy

The metadata contains three different delta mechanisms across four DataSources. In a BW-to-Databricks migration, each one requires a different replacement strategy — and two of them are BW-proprietary with no direct Databricks equivalent. Ask Bob to surface the problem:

Type this in the Bob chat:

@/BW Metadata/BW Metadata.txt
This metadata has three distinct delta mechanisms: ODP_DELTA (used by ZDS_COPA_CDS_ACTUALS and ZDS_COPA_COSTCENTER), Standard Delta AIE (used by 0FI_GL_14), and no delta at all (ZEXT_NIELSEN flat file).

For each mechanism:
1. Explain exactly how delta works in BW — what tracks changes, what gets extracted on each run
2. Why does this mechanism not exist in Databricks, and what must replace it?
3. What is the specific technical risk of the replacement — what could silently go wrong that would only be discovered at period-end close?

Be specific. Use the field names and technical object names from the metadata.
✅ You should see — Bob distinguishing ODP subscription queues from Standard Delta change pointers, explaining why both are BW-proprietary, and naming concrete failure modes (e.g. back-dated GL postings lost on a BUDAT watermark, ODP queue orphan records if the subscriber is deregistered mid-migration).
💡 As a BW architect, this is the delta mechanism review you would normally do over a day with the BW BASIS team. Bob just did it in 60 seconds from the metadata. Your job now is to verify whether its answer is correct — and correct it where it is not.

@/BW Metadata/BW Metadata.txt
The transformation T1 contains an ABAP routine called COMPUTE_GROSS_MARGIN_AND_DQ. Read the routine code in the metadata and answer:

1. The FX conversion uses CONVERT_TO_LOCAL_CURRENCY with sy-datum as the date. What is the problem with using sy-datum in a batch delta load, and what should the Databricks replacement use instead?
2. The DQ routine routes records with ZDQ_FLAG = '2' (REJECT) to a monitor table and to HCPA_ERR01. In Databricks, there is no BW monitor table. What is the equivalent pattern and what must the Finance Operations team be told about how to access rejected records after migration?

✅ You should see — Bob flagging sy-datum as the run date (not the posting date), recommending the Databricks replacement use BUDAT / posting date for rate lookup; explaining the Delta Lake error table pattern as the HCPA_ERR01 equivalent; and flagging the LC fallback as a financial reporting risk that needs Finance sign-off.

4 Challenge the Architecture

Three separate transformation streams (T1 actuals, T2 cost center overhead, T3 GL recon) all converge into the same ADSO — HCPA_AD01. This multi-record-type convergence pattern is common in BW but creates a specific migration problem in Databricks. Ask Bob to reason through it:

Type this in the Bob chat:

@/BW Metadata/BW Metadata.txt
The ADSO HCPA_AD01 receives records from three transformations: T1 (COPA actuals from ZDS_COPA_CDS_ACTUALS), T2 (cost center overhead from ZDS_COPA_COSTCENTER), and T3 (GL reconciliation records from 0FI_GL_14). Each stream loads different record types distinguished by ZREC_TYPE.

This is a multi-record-type convergence pattern — three pipelines writing to one table.

Answer:
1. In BW, the ADSO handles this naturally because all three DTPs write to the same ADSO using the BW request mechanism. In Databricks, three independent pipelines write to the same Delta table. What concurrency and ordering problems does this create, and how should the pipeline orchestration be designed to prevent them?
2. T3 contains a GL vs COPA reconciliation step that reads from HCPA_AD01 while also writing to it. In Databricks, a pipeline cannot read from and write to the same table in the same transaction. How must this step be redesigned?
3. If we split HCPA_AD01 into three separate Silver tables (one per record type) instead of the single convergence model, what are the downstream impacts on T4 and the CompositeProvider equivalent?

Give a recommendation for each, not just an analysis.
✅ You should see — Bob recommending sequential pipeline execution with dependency ordering (not parallel writes), a two-step T3 redesign separating the GL read from the COPA write, and an analysis of whether splitting HCPA_AD01 simplifies or complicates the T4 merge.
💡 This is the key insight. Bob identified the intra-ADSO read anti-pattern and the convergence orchestration problem from raw metadata. That analysis typically comes out of a 2-day architecture review workshop. You now have a first-draft recommendation to challenge, refine, or push back on — in 16 minutes.
