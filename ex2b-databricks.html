Databricks Track

Interrogate the Migration Architecture

Read the artefacts like an architect. Ask hard questions. Challenge the design. Bob as your technical peer reviewer.

⏱ 16 minutes 🏗️ Databricks / Architecture team
🏠 Start 1 · Basics 2B · Databricks 3 · MCP ⭐ Finale

📋 What You're Working With

Your starter kit contains four artefacts from a real BW-to-Databricks migration design for Heineken's COPA Profitability Analytics platform. These are not mock data — they are a working Databricks Foundation design with real SQL, real business rules, and real complexity scores.

💡 Your artefacts:
  • D1 — Unity Catalog layout: Bronze / Silver / Gold schemas and table mapping
  • D3 — Silver layer SQL: transformations implementing 14 business rules, including ⚠️ BW-ONLY PATTERN flags where SAP logic has no direct Databricks equivalent
  • D4 — Gold layer: central fact table DDL + semantic views for Power BI (52.6M rows, replaces HCPA_AD03)
  • D8 — Migration effort estimate: 38 objects scored LOW / MEDIUM / HIGH with day estimates and key risks

In this exercise you will interrogate the architecture, identify design decisions worth challenging, validate the foundation quality, and produce outputs that feed directly into the Finale.

1 Find the Risky Design Decisions

The Silver layer SQL contains several places where BW-proprietary patterns had to be redesigned. Ask Bob to surface them and explain the risk each one carries:

Type this in the Bob chat:

@/Databricks - Foundation/D3 - Silver Layer DDL and Transformation SQL.md
This file contains markers for BW-ONLY PATTERN — places where SAP BW logic has no direct Databricks equivalent and had to be redesigned.

List every BW-ONLY PATTERN you find. For each one:
1. What BW pattern is being replaced
2. What the Databricks replacement is
3. What could go wrong if the replacement is not validated correctly
4. Your assessment: is this replacement adequate, or does it need more design work?
✅ You should see — a structured list of BW-specific patterns (ODP delta queues, HANA Calc Views, intra-ADSO reads) with Bob's assessment of each replacement's adequacy. Look for patterns where Bob flags residual risk.
💡 As an architect, this is the kind of review that typically takes a day of reading SQL files. Bob just did it in 60 seconds. Now you can spend your time on the judgement calls, not the reading.

2 Challenge the Effort Estimate

D8 contains 38 stories with complexity scores and day estimates. As a PO or architect, your job is to challenge the assumptions. Ask Bob to stress-test the estimate:

Type this in the Bob chat:

@/Databricks - Foundation/D8 - Migration Effort Estimate.md
I want to challenge this effort estimate. Answer the following:

1. Which HIGH complexity objects have the most dependencies on other objects completing first? Identify the critical path — if these slip, what else slips with them?
2. Which estimates look undercooked — where the complexity is HIGH but the day estimate seems low relative to the risk described?
3. If we had to cut scope to deliver in 3 sprints (30 working days) instead of the full estimate, which objects would you defer and why?

Be direct. Flag genuine concerns, not just observations.
✅ You should see — Bob identifying the critical path (Bronze ingestion → Silver T1 FX/DQ → Gold fact → parallel run), flagging any estimates that look thin, and proposing a credible MVP scope for 3 sprints.
⚠️ VM performance note. This prompt crosses two sections of D8. On the VM it may take 30–60 seconds to respond. Watch for output appearing progressively.

3 Run the Quality Gate

Before any migration proceeds, the Foundation artefacts should pass a formal quality check. Run the validation skill — it performs 8 automated checks and produces a RAG scorecard.

Type this in the Bob chat:

run quick validation
⚠️ VM performance note. The validation skill reads multiple artefact files and runs 8 checks. On the VM this may take 60–90 seconds. Do not re-run while it is working.
✅ You should see — a RAG scorecard table (8 checks, pass/fail, overall GREEN / AMBER / RED) and a file saved as D9 - Foundation Validation Report.md.
⚠️ Skill didn't fire? Try: Validate my migration artifacts — use Quick Mode

Once the scorecard appears, ask Bob one follow-up question about it:

Type this in the Bob chat:

Based on the validation scorecard, which finding would you prioritise fixing before the first sprint begins, and what is the one-line action needed to fix it?
✅ You should see — Bob picking the most material finding from the scorecard and giving a concrete, actionable fix. This is Bob as Quality Gatekeeper — reasoning over the output it just generated.

4 Produce a Stakeholder-Ready Summary

Bring together the architecture review, the effort challenge, and the validation findings into one crisp output a Finance Controller or Programme Director can read:

Type this in the Bob chat:

@/Databricks - Foundation/D3 - Silver Layer DDL and Transformation SQL.md
@/Databricks - Foundation/D8 - Migration Effort Estimate.md
Based on the architecture review, effort estimate analysis, and validation scorecard from this session, write a 5-bullet executive summary for a Finance Controller who will sponsor this migration.

Each bullet must be one sentence. Cover:
1. What we are building and what it replaces
2. The single highest technical risk and how it is being managed
3. The overall effort and timeline in plain business language (no story points, no SQL)
4. The one decision still open that requires Finance sign-off before Sprint 1 begins
5. The recommended next step

No jargon. No acronyms without explanation.
✅ You should see — five crisp, business-language sentences that synthesise everything from this session into a sponsor-ready update.
💡 This is the multiplier. Bob read the SQL, reviewed the effort estimate, ran a quality check, and now drafted the sponsor communication — all from the same four files, in the same session. Each of those tasks is something you would normally hand to a different person.
⭐ Stretch Task — Interrogate the Gold Layer Design (if you finish early)

The Gold layer (D4) defines the central fact table that Power BI connects to. It implements BR-13 (Variance) and BR-14 (EBITDA) as SQL expressions. As an architect, ask Bob to stress-test the semantic design:

Type this in the Bob chat:

@/Databricks - Foundation/D4 - Gold Layer DDL and Views.md
Review the Gold layer design and answer:
1. The design implements EBITDA as: gross_margin minus cost_amt. What assumption does this make, and what could cause it to diverge from the Finance team's official EBITDA definition?
2. The copa_query_layer_vw has a 12-second SLA. What risks does a DirectQuery Power BI connection to a 52.6M row table carry, and what would you recommend to mitigate them?
3. Is there anything in this design that a Finance Controller should formally sign off on before go-live?
